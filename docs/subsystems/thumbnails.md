# Thumbnails

Implementation entry points: [rendering and tool probes](../../src-tauri/src/thumbs.rs), [scheduler](../../src-tauri/src/services/thumb_scheduler.rs), [publication and cleanup](../../src-tauri/src/services/thumb_service.rs), [`thumb://` protocol](../../src-tauri/src/services/thumb_protocol.rs), [frontend image](../../src/ui/controls/ThumbnailImage.tsx). Decision record: [ADR 0006](../adr/0006-thumb-uri-scheme.md).

This page owns JPEG preview identity, rendering, tool discovery, scheduling, publication, retries, cancellation, and per-tile updates. Thumbnail files and their database references have separate commit boundaries.

Command names, payload shapes, channel serialization, and shared progress-event rules live in the [IPC contract](../architecture/ipc-contract.md). Database schema and transaction conventions live in [database persistence](database.md), scan-time metadata and fingerprints in [scanning and indexing](scanning-and-indexing.md), gallery range loading and presentation in [library query and gallery](library-query-and-gallery.md), and app-data, resource, and lock lifecycles in the [system overview](../architecture/system-overview.md).

`ThumbnailImage` requests `thumb://` images with `crossorigin="anonymous"`, and the
protocol answers with `Access-Control-Allow-Origin` set to the requesting page origin
(`tauri://localhost`, or `http://localhost:1420` in development). WebKitGTK needs CORS mode
at the HTTP development origin. The shared component covers gallery, duplicate and
group-order previews.

## Source versions, cache and target identity

Every thumbnail job carries a `SourceVersion` — the exact source identity of `path`, `size_bytes`, and nanosecond `fingerprint_mtime_ns` read from SQLite when the task was created. The version travels through the scheduler task, is echoed back in the result, and acts as the compare-and-set guard for every database write. The database compare-and-set rejects a result whose source version no longer matches. File publication happens earlier and stale produced files are removed best-effort after that check.

The thumbnail directory is `<app-data>/thumbs` and is created at startup. `thumb_target` hashes these bytes with SHA-256:

1. the cache schema version (`THUMB_CACHE_VERSION = 3`) encoded little-endian;
2. a zero separator byte;
3. the source path's lossy UTF-8 representation;
4. a zero separator byte;
5. the source's signed 64-bit `size_bytes`; and
6. the source's signed 64-bit `fingerprint_mtime_ns`.

The target is the lowercase hexadecimal digest plus `.jpg`. Asset ID, media kind, render settings, and file contents are not part of the key. The path makes one source version converge on one target across `thumb://` requests and bulk entry points. A target already present on disk is treated as ready and its path is reconciled into SQLite through the same version guard.

Cache version 2 added the nanosecond mtime; version 3 applies the EXIF orientation of images ([ADR 0020](../adr/0020-exif-orientation-and-legacy-thumbnail-adoption.md)). A recorded `thumb_path` equal to the current target is served as is. Any other recorded path is a legacy reference (an earlier cache version, or a restored file) and is not served as current from the request section: the request or Render all hands it to the render worker as the task's `legacy_thumb` when it is an owned file (regular, not a symlink, inside the canonical thumbnail root). The worker checks the source outside the thumbnail read section, so a hung mount cannot hold the guard, and it checks ownership again (inside the target's canonical directory) right before it moves, removes or serves the file. For an unreachable source it returns the recorded file, which is served without a database write and labelled with no version, so the response is `no-store` and WebKit asks again once the source is back. Otherwise it moves the file to the current target when the current rules draw the same picture (a video, or an image without an EXIF transform or with unreadable metadata), and renders the target and removes the legacy file when they do not. If changing the key or renderer again, explicitly decide how to treat old references and remove unreferenced files. Current cleanup is reference-driven and does not sweep every old cache file.

When an incremental scan re-indexes a changed file whose seconds-resolution `modified_at` did not move (same-second modification), `upsert_scanned_asset` releases the stored `thumb_path` whenever the precise fingerprint value differs, so a superseded reference cannot survive the scan.

### Cache provenance in gallery measurements

The [gallery performance suite](../development/testing.md#gallery-performance-measurements) clears the isolated library and thumbnail files before indexing synthetic fixtures. Startup and filtering can already generate visible and prefetched previews, so the timing record includes the initial mounted IDs and a file inventory before sampling. It samples a new image route before metadata/edit traversal, and repeats the same route with the same filter.

Each scroll sample inventories final JPEGs outside the timed interval and compares that inventory with the filenames of decoded visible previews. This includes files published before their database reference. A first-use preview sample has no visible target in that inventory; a revisit requires all visible targets to exist. Prefetched or overlapping mixed samples remain recorded separately. The snapshot does not establish whether a render was already queued or whether source bytes were in the operating system cache. No OS-cache flush is performed. Preview-file reuse also does not imply frontend summary-page retention, because the route crosses its eviction bound.

## Image and GIF rendering

Images and GIFs produce an RGB JPEG. A JPEG source (detected by its `FF D8 FF` signature) is decoded with `jpeg-decoder` at the smallest IDCT scale (1/8, 1/4, 1/2 or 1) that still covers the thumbnail: the longer side for normal images, the crop width for tall ones. The crate is built with `platform_independent` and without default features, so it contains no `unsafe` code and starts no rayon pool. CMYK and 16-bit JPEGs, and any `jpeg-decoder` error, fall back to the general decoder. Every other format goes through the `image` decoder, which reads the dimensions from the header of the same open file. In both paths a source whose header pixel count exceeds `MAX_DECODE_PIXELS` (50 megapixels) fails the job with a controlled error before the pixel decode.

Both paths return the image in its displayed orientation, as the lightbox shows the original ([ADR 0020](../adr/0020-exif-orientation-and-legacy-thumbnail-adoption.md)). The scaled JPEG path reads the EXIF Orientation from the APP1 segment that `read_info` parses before the frame header, chooses the IDCT scale for the displayed size (axes swapped for quarter turns), and rotates or mirrors the scaled buffer. The general path uses the decoder's reported orientation (EXIF in JPEG, PNG `eXIf` and WebP) and, when there is a transform, first shrinks the decoded image to the same request so the rotation copies a small buffer. Missing or invalid orientation metadata means no transform. The crop rule below is decided on the displayed size, so a source stored landscape whose rotated height is at least 1.6 times its width gets the top-biased square crop. `thumbs::image_orientation` reads the same orientation from the header only; the render worker uses it to decide whether a legacy thumbnail can be adopted.

Scaled decoding does not skip Huffman entropy decoding, which dominates large JPEGs: a synthetic 24 MP JPEG takes about 78 ms in release instead of 98 ms, and the gain comes mostly from not resizing a full-resolution buffer ([ADR 0006](../adr/0006-thumb-uri-scheme.md)). The maximum normal thumbnail box is 390 by 390 pixels. A portrait with `height / width >= 1.6` is handled specially: a square as wide as the source is cropped from `x = 0`, with its top at `min(96, height - width)`, and resized exactly to 390 by 390 with a Triangle filter. Other images use aspect-preserving `thumbnail(390, 390)`. The gallery applies `object-cover` when presenting the result.

Rendering creates the parent directory, removes any old sibling temporary file, and writes `<target-stem>.tmp.jpg`. Publication renames that file to the final target. If the final target appeared before publication, the temporary file is removed and the existing target wins. Callers see a target only after the JPEG write completed; temporary files are never stored in `assets.thumb_path`.

## Video probing and rendering

Video duration is collected during indexing. The probe tries derived `ffprobe` candidates in order and accepts the first finite, non-negative duration, rounded to milliseconds. If none succeeds, it invokes the resolved `ffmpeg` and parses the duration from stderr. Every probe process has a 12-second timeout. Pipe readers drain stdout and stderr while the child runs and retain at most 64 KiB per stream. Timeout/error paths terminate and reap the child before returning.

The render seek is chosen from the stored duration:

| Duration | Seek |
| --- | --- |
| missing | 1 second |
| non-positive | 0 |
| below 1 second | 80% of duration |
| 1 to below 5 seconds | 1 second |
| 5 to below 10 seconds | 1 second before the end |
| 10 seconds or more | 10 seconds, clamped just before the end |

The clamp keeps a known positive seek at most `duration - 0.001` seconds. Rendering runs `ffmpeg` with one decoder thread, no stdin, audio, subtitles, or data, selects one frame, scales it to width 390 while preserving aspect ratio, uses JPEG quality value 7, and writes through the same temporary-publication path as images. Each attempt times out after 45 seconds. A job makes up to three attempts and stops at the first that publishes a target:

1. `Keyframe` at the chosen seek: `-skip_frame nokey -noaccurate_seek` decodes keyframes only and takes the keyframe the input seek lands on, about 4x faster than decoding the GOP up to the exact time (202 ms to 48 ms on a synthetic 1080p H.264 clip with 250-frame GOPs);
2. `Exact` at the chosen seek, because some inputs yield no frame in keyframe mode (for example a 0.5 s clip with a single keyframe);
3. `Exact` at zero seconds, only when the chosen seek is positive.

Both probing and rendering poll child completion every 25 ms. A timed-out child is killed and waited on.

## ffmpeg and ffprobe discovery

At startup, ffmpeg discovery searches the resource directory and its `binaries` child, then equivalent executable-adjacent and `resources` locations. In each directory it considers `ffmpeg`; it then checks `/usr/bin/ffmpeg` and finally falls back to `PATH`.

Flatpak installs the tools beside the executable in `/app/bin`. AppImage carries them in its `usr/bin`. These layouts use the same discovery logic; package builds verify both tools can execute.

For a probe, `ffprobe_candidates` tries a sibling name derived from the ffmpeg filename, a plain sibling `ffprobe`, bare `ffprobe` through `PATH`, then `/usr/bin/ffprobe`, removing duplicates. Failed probes fall back to the resolved ffmpeg's stderr duration. A missing or unlaunchable tool leaves duration absent or rendering failed without itself preventing startup.

`get_video_tool_status` uses the same candidate builder. It runs `-version` with a three-second timeout per candidate and returns separate availability booleans. Settings reads these once when its shell-lived scan controller mounts. This is an executable check, not proof that a particular file decodes or native playback works.

## Shared scheduler

One process-wide `ThumbnailScheduler` detects logical CPU capacity at startup with Rust's `available_parallelism()`. If detection fails, both modes use four workers. Browsing retains its total concurrency of `available_parallelism - 2`, clamped to 2 through 8, and at most two simultaneous videos. A video job that carries a legacy thumbnail does not count against the video cap, because it normally only renames that file; if the rename fails it renders outside the cap. Bulk rendering uses one worker per available logical CPU for both total jobs and videos. The pool starts enough threads for the larger of the browsing and bulk limits; extra threads wait on the scheduler condition variable while browsing. The explicit worker-count constructor still enforces at least one worker for tests and direct callers. Startup refuses to launch the application when any worker thread fails to spawn.

The scheduler has three queues. `Interactive` (visible `thumb://` requests) is LIFO: a new or repeated request goes to the front, so tiles that just came into view render before ones scrolled past. `High` (FIFO) takes `thumb://` prefetch requests from overscan tiles, and `Low` (FIFO) bulk work. A tile that scrolls into view before its prefetch arrived asks again without `p=1` (see [frontend tiles](#frontend-tiles)), so High holds only tiles that have not been visible, and FIFO renders the overscan rows ahead of a steady scroll nearest first ([ADR 0021](../adr/0021-visible-tiles-drop-a-pending-prefetch.md)). Workers search Interactive, then High, then Low, but may pass a blocked video and run another eligible job. A request for a queued target with a stronger priority moves it to that queue (Low to High, or either to the front of Interactive). Work already running cannot be preempted or cancelled: WebKitGTK gives custom-scheme handlers no cancellation signal, so every request is answered and LIFO is the only defence against renders for tiles that are gone.

Jobs are keyed by the target path string. Enqueuing an existing target job attaches a waiter rather than starting another render, up to 256 waiters per target; the next enqueue fails fast. Each waiter retains its own asset ID and receives the shared result, either through a channel (bulk) or through a callback run on the worker thread (`enqueue_with_callback`, used by `thumb://` so no thread waits for a render). A panicking callback is caught. This de-duplicates work across entry points while bounding fan-out memory. Workers admit new jobs only below the active mode's total and video limits. Completion removes the job, decrements total-job and video accounting, wakes blocked workers, and sends the result to all waiters. A dropped receiver is ignored.

The processor uses `catch_unwind` so a job panic becomes a failed result and the worker loop continues. `MAX_PENDING_JOBS = 2048` bounds distinct queued and running jobs together; further enqueues fail with a queue-full error. Demand waits also have the deadlines described below. These controls do not make decoding or process shutdown infallible.

## The `thumb://` protocol

Gallery tiles, duplicate cards and group-order previews load `thumb://localhost/<id>?v=<version>[&c=1][&p=1][&r=<n>]`, built only by `thumbnailUrl` in `src/platform/tauri/thumbnails.ts`. The handler (`services/thumb_protocol.rs`, registered with `register_asynchronous_uri_scheme_protocol` on the builder) runs on the GTK main thread, so it only parses and hands the request to the blocking pool.

- **Parameters.** The path is a positive decimal asset ID (at most 19 digits). `v` is the 16-hex-character `thumb_version` token. `c=1` asks for a cached file only. `p=1` marks a prefetch (overscan) request. `r=<1-3 digits>` is a frontend retry counter that only busts the WebKit cache (sent at most once). Anything else, a repeated parameter, or a non-GET method is `400`. The scheme never accepts a path.
- **Version token.** `thumb_version` is the first 16 hex characters of the cache key, so it is a prefix of the target file stem and a URL changes exactly when the thumbnail file would. Summaries (`AssetSummary`) and duplicate assets carry it; the backend computes it from `path`, `size_bytes` and `fingerprint_mtime_ns` while reading the row.
- **Existing file.** One short `thumb_read_section` reads the row (`get_assets_for_thumbnails_by_ids`) and the file bytes, so clear, delete and rename cannot remove the file between the check and the read. A recorded path that is the current target and still exists is served without a write, unless a stale failure marker must be cleared. A target found on disk without a database reference is published through `commit_thumbnail_results` and served. A recorded legacy path that is an owned file is not read here and the source is not checked: the request continues as a missing file, with no `SOURCE_MISSING` check, and the render task carries the legacy file (see [source versions](#source-versions-cache-and-target-identity)). A result that keeps the recorded path of a row without a failure marker is served without a write.
- **Missing file.** A render is enqueued with a callback and the section ends: at `Interactive` (LIFO), or at `High` (FIFO, behind every Interactive job) for `p=1`. Another request for the same asset joins that job as a further waiter, and a request without `p=1` moves a queued prefetch to the front of Interactive; each request gets its own response from the one render. When the render finishes, the callback hands it to a publisher that commits every result already waiting (at most 64) in one transaction on the blocking pool, through the usual compare-and-set and generation check, then reads each file and responds. Ordinary connections run WAL with `synchronous=NORMAL`, so a commit costs no fsync; grouping only reduces `IMMEDIATE` write-lock acquisitions while a scan writes. A lost compare-and-set or a clear in between answers `404`; the frontend's retry then renders again.
- **Failures.** A missing source writes a failure marker and answers `404`. A failure marker from an earlier run gets one on-demand retry per process; a render that failed in this process (`ThumbnailScheduler::failed_interactively`, keyed by asset ID and `record_version`) answers `404` without rendering again, so a broken video does not occupy a video slot on every tile mount. The settings action "render failed thumbnails" ignores this memory.
- **Cached only.** With `c=1` an existing current target is served and anything else is `404`; nothing is enqueued or written. A legacy reference is a `404` too, so no old picture is cached under the new URL and the source is not checked; the tile switches to the rendering URL after the pause. Tiles use it during a fast-scroll pause.
- **Responses.** `200 image/jpeg` with `Cache-Control: public, max-age=31536000, immutable` when the served version matches `v`; a stale URL gets the current picture with `no-store`. `404`, `400` and `503` (state not managed yet, maintenance admission error, or a full scheduler queue, with `Retry-After: 1`) are `no-store`. Every response carries `Access-Control-Allow-Origin` for an allowed origin.

The handler admits a database operation per request and holds no lock across an await; the scheduler task keeps its permit until the render ends, as before.

## Bulk render, retry, and cancellation

Only one `render_all_thumbnails` or `render_failed_thumbnails` operation may coordinate work at a time. Both automatically enter the shared scheduler's bulk mode, including for video thumbnails. There is no worker-count preference or dialog. A scoped guard restores browsing admission on success, cancellation, error, or panic; another guard clears the running and cancellation flags. Already-running jobs finish, and new jobs start only when the restored total and video limits permit them. Gallery requests retain high priority and share target deduplication with bulk jobs.

The coordinator keeps at most `min(2048, max(24, 3 × CPU count))` scheduler results pending. For example, 16 CPUs permit 16 simultaneous renders and a 48-result submission window; 32 CPUs permit 32 simultaneous renders and a 96-result window. The scheduler-wide 2,048-job bound still applies across all callers. CPU count means logical CPUs available to this process at startup; decoding and storage can limit actual throughput.

Both bulk modes fetch keyset pages sized to the larger of 512 assets and the submission window, capped at 2,048 rows by the database helper. Pages include failure eligibility and stop at the maximum asset ID observed at the start. They release read cursors/connections before waiting for render results. Render-all counts an existing current target as generated and publishes it only when the row does not already record that path or has a failure marker for its `record_version`, so an already-rendered library costs no SQLite write. A source that `Path::exists` cannot see (an unmounted drive or an unreadable folder, which look the same) keeps a recorded thumbnail that is still a regular file inside the canonical thumbnail root (`thumb_path` is untrusted): it is counted as generated, its file and `thumb_path` stay, and no failure marker is written (a stale one is cleared, as the demand path does), so the next run after the source is back finds the current target without rendering, or renders a new one when the kept file was not the current target, instead of skipping the asset as failed ([ADR 0018](../adr/0018-render-all-keeps-thumbnails-of-unreachable-sources.md)). Only a missing source without such a file records a failure; a recorded path outside the root is cleared but its file is never removed. Render-all skips eligible failures whose target does not exist. A reachable source whose current target is missing is enqueued with its owned legacy reference, so after a cache-version bump the worker adopts unchanged pictures instead of redrawing the library. Retry-failed selects only failures whose `source_record_version` matches the asset, in asset-ID order. Success clears only that version's failure marker; an older worker cannot overwrite or clear a newer failure.

Each page drains its pending jobs and then publishes its collected paths and failure markers in IMMEDIATE transactions of at most 256 results. Each transaction yields to pending user metadata writes first (at most 250 ms) and runs under the shared thumbnail guard. The source compare-and-set and clear epoch reject obsolete updates; rejected IDs contribute to the separate stale count. A clear since the page was read also moves that page's unwritten current rows from generated to stale. The 180-second result-stall deadline remains in effect. Progress counts describe this evolving library; concurrent scans can alter eligibility after the initial count.

Cancellation is cooperative. `cancel_render_all_thumbnails` returns `false` when no bulk coordinator is running; otherwise it sets an atomic flag and returns `true` directly, without waiting for admission, workflow locks, or a blocking worker. The coordinator checks before each enqueue and while waiting for results at 50 ms intervals. On cancellation it stops enqueueing/waiting, drains results already ready, batch-commits the collected path updates, emits the mode's done phase, and returns a summary with `cancelled: true` and possibly `processed < total`.

The frontend associates each Stop request with the active render token. Success, `false`, and rejection may update settings feedback only until that render action finishes, including its library refresh. Late replies preserve terminal results and subsequent operations' progress. Finishing a render resets its Stop state; cleanup from an old reply cannot clear a newer render's pending Stop. This is frontend publication ownership; the cancellation command still has no job identifier. See [settings cancellation](settings-operations.md#thumbnail-bulk-actions-and-cancellation).

Scheduler jobs already queued or running are not removed or killed by bulk cancellation. They may still publish files after the bulk command returns, but results not ready during the nonblocking drain are not included in that bulk summary or database batch; those late files have no database publication from the completed coordinator. Scheduler tasks retain their operation permit until their file work finishes, so database maintenance drains them too. A later demand call discovers such a target on disk and reconciles its path.

## Generation epoch

`clear_all_thumbnails` bumps the process-wide `thumbnail_generation` counter under the exclusive thumbnail lock.

- `thumb://` requests capture that epoch in the guarded section that reads their row. Bulk coordinators capture it with each candidate page.
- Every publication rechecks the epoch under the shared guard. A changed epoch skips those writes and reports them stale per captured epoch: jobs are keyed by target, so a request made after a clear can join a pre-clear job of the same asset, and only the pre-clear waiter is stale. Its produced file is removed only when the row is gone or its source version changed meanwhile; a target of a still-current version stays for the post-clear waiter or a later request to publish ([ADR 0019](../adr/0019-clear-epoch-keeps-current-version-targets.md)).
- Coordinators do not hold the guard while they wait for the scheduler, so a clear can run between their sections. Results rendered before it are then dropped. In bulk, only the pages that started before the clear are dropped.
- Scheduler jobs left behind by cancellation can still create unreferenced files after a coordinator returns.

## Frontend tiles

There is no frontend thumbnail queue or store. A tile sets its `<img>` `src` to the `thumb://` URL of its asset; WebKit requests, caches and decodes it. `ThumbnailImage` keeps one `<img>` per component, hides it until the current source has loaded, and retries a failed load twice (after 500 ms and 2 s) through `retrySrc`, which appends `r=<n>`. After these quick retries it shows a transparent placeholder and calls `onFailed`, once for that showing of the source. An `<img>` error carries no status, so a transient `503` (full scheduler queue) cannot be told from a final `404`: while the component stays mounted with the same `src`, it keeps retrying after 4 s, 8 s, 16 s and then every 30 s, with the placeholder between attempts, until a load shows the picture and reports `onReady`. `r` cycles through 1 to 999. At most one timer per component is pending; it is cleared on unmount and on a `src` change. Load, retry and failure state belong to the `src` they were observed for, so recycled cells never show another asset's picture, and they are keyed by each change of the `src` string (a refreshed summary with the same URL keeps a pending retry): a source that comes back to the same recycled cell is requested again instead of answered by the placeholder ([ADR 0024](../adr/0024-thumbnail-retries-continue-while-the-tile-is-mounted.md)). Without `retrySrc` (cached only) a failure is final for that showing.

The tile spinner is CSS only: `.thumbnail-loader` follows the image and is displayed while the image is still `invisible`, fading in after 300 ms so cached thumbnails never flash it.

An asset first shown in an overscan tile (outside the visible index range) requests `p=1`, so the four overscan rows above and below the viewport render only after every visible tile. During a fast-scroll pause, an asset first shown in a tile requests `c=1` (cached only). Both choices stick for the asset in that tile, so a picture that has loaded keeps its URL when it scrolls into view and is never reloaded. Each choice has one one-way exit. A cached-only hit keeps its URL after the pause; a miss (404) switches to the rendering URL once the pause ends. A prefetch whose picture has neither shown nor finally failed drops `p=1` when its tile is inside the visible rows, outside a pause and after any cached-only miss: the new URL joins the queued render and moves it to the front of Interactive, so the tiles visible where a steady scroll stops render first instead of after every tile scrolled past ([ADR 0021](../adr/0021-visible-tiles-drop-a-pending-prefetch.md)). The flag never comes back for that asset in that tile. `ThumbnailImage` reports a shown picture through `onReady`, also for a cached picture that is complete without a load event, and never for the failure placeholder. Assets shown outside a pause use the rendering URL at once. Refresh, query changes and page eviction do not touch thumbnails: summaries carry `thumb_version`, so fallback rows after a refresh show their pictures too. See [pause thresholds and range publication](library-query-and-gallery.md#virtual-range-loading-and-thumbnail-prefetch).

## Locks, progress, cleanup, and database consistency

Generation and bulk retry commands enter through `with_thumb_operation`, which admits the operation without a lock; `thumb://` requests admit their own permit. The services then take the shared read guard (`thumb_read_section`) only for short sections: reading rows or candidate pages, deciding and enqueueing jobs, committing a publication, and removing files. They never hold it while waiting for scheduler results. A waiting exclusive writer therefore waits for at most one such section, and new thumbnail work waits only for that writer, not for a render that may take up to ~90 s for video ([ADR 0002](../adr/0002-backend-write-priority-and-scan-revisions.md)). Bulk cancellation takes no workflow lock and only sets the cancellation flag. `clear_all_thumbnails` takes the write lock, so it waits for active readers and excludes new ones while it clears. Root removal, asset delete/rename, database bundle operations, and library clearing use the combined scan lock then thumbnail write lock where they touch thumbnail ownership. The lock ordering and process isolation are defined in the [system overview](../architecture/system-overview.md).

All thumbnail commands run on Tauri's blocking thread pool (`spawn_blocking`): each command acquires its workflow lock inside the blocking task, so no lock is ever held across an await and no async runtime thread is occupied by scheduler waits or SQLite work. Workflow locks recover from poisoning (`into_inner`) instead of rejecting every later command after a panicked holder; the thumbnail processor's panic guard additionally keeps scheduler state unpoisoned in practice.

Every cleanup path, including stale-result cleanup at publication, treats `assets.thumb_path` as untrusted persisted data. Before deletion it canonicalizes the configured thumbnail root (once per operation) and the candidate, rejects symlinks and non-files, and requires the canonical candidate to remain below the canonical thumbnail root. Missing, invalid, or outside-root paths count as unsuccessful best-effort cleanup and are never passed to `remove_file`.

Bulk runs emit start, mode-specific progress, warning, and done phases; progress is emitted every 25 processed assets and at completion. `thumb://` requests emit no progress. Cleanup reports every 25 paths and at completion. All use the shared best-effort `process-progress` broadcast; command/channel results remain authoritative.

A `thumb://` render publishes its result right after it arrives, before the response. Bulk results commit per candidate page after processing or cancellation drain. In every case the path and the failure marker commit in one transaction, and a database error there rejects the command. A compare-and-set that loses against a re-index skips the write and best-effort deletes the produced file; a generation reset skips the write and deletes the file only when its source version is no longer current. Existing files can therefore temporarily precede their database references. Clear all first clears database paths and failures, then walks the owned thumbnail directory without following symlinks and best-effort removes its regular files, including unreferenced old versions and temporary files. A first walk only counts the regular files for the progress total; the second walk deletes as it goes, so no path list is held under the exclusive lock. Files that appear or vanish between the walks (a render still finishing) never make `processed` exceed `total`, and the last event reports the actual count. Each nested directory is removed, when empty, as the walk reaches it after its files; the root is retained. Every file still passes the canonical-root containment guard. Enumeration failures and deletion failures are best effort; the count includes only removed files, not directories or skipped symlinks. A failed file removal leaves an unreferenced file; the reported removal count includes only successful deletions.

Asset/root deletion and rename clear related rows and best-effort remove known thumbnail files. Successful completed scan cleanup removes stale asset and failure rows, but ordinary rescans do not sweep unreferenced old-version targets from the thumbnail directory. Thumbnail path writes and clears do not bump the library revision because they do not change query membership or order.

## Known limitations

- Thumbnail identity covers path, size, and nanosecond mtime under cache version 3. Content is not hashed, so changed bytes with unchanged identity reuse a target. A legacy reference is adopted or redrawn by the render worker; the adoption check covers only the EXIF orientation of version 3, so a later renderer change needs its own decision. The scaled JPEG decode, Triangle crop filter and keyframe video frames did not bump the version: existing thumbnails stay valid pictures of the same source ([ADR 0006](../adr/0006-thumb-uri-scheme.md)).
- The orientation probe and the scaled JPEG path read EXIF only before the frame header, where the Exif standard places it. A non-conforming JPEG with APP1 after SOF stays unrotated on that path. A legacy file whose redraw fails is left unreferenced until Clear all.
- The indexed `width` and `height` are the stored (unrotated) dimensions from `image::image_dimensions`.
- Bulk cancellation does not remove shared scheduler jobs. Queued work can consume CPU and publish files afterward. Only results collected by the coordinator receive its version-checked database update; later demand can reconcile an existing target.
- The scheduler has no shutdown protocol; workers live for the whole process lifetime.
- Browsing video rendering is capped at two active jobs in code, but there is no focused test for that cap or for choosing a runnable image behind blocked videos. Process regressions now cover draining both output pipes, diagnostic caps, and timeout reaping; resource/PATH discovery and all fallback combinations remain unverified.
- Progress broadcasts are best effort. WebKitGTK does not cancel custom-scheme requests, so a render for a tile that is gone still runs; LIFO order and the cached-only pause bound the waste. A full queue answers `503`; a refused visible tile shows the placeholder after 2.5 s and picks the picture up within 30 s of the queue accepting it again.
- A tile whose thumbnail fails for good sends one request about every 30 s while it is mounted. The backend answers it without rendering (failure memory), but a missing source costs a `Path::exists` and a failure-marker write per request ([ADR 0024](../adr/0024-thumbnail-retries-continue-while-the-tile-is-mounted.md)).
- A tile that drops `p=1` sends a second `thumb://` request for the same job: one more row read, file read and response, never a second render. Tiles that came into view during a steady scroll stay at Interactive after they scroll past. Under overload they keep the overscan rows ahead from rendering during the scroll, so rows arrive unrendered and are drawn after they come into view, and after a stop they render (newest first) before the overscan rows ahead. Measurements and the rejected LIFO High queue are in [ADR 0021](../adr/0021-visible-tiles-drop-a-pending-prefetch.md).
- A render that failed in this process is not retried on demand until restart or the explicit "render failed thumbnails" action.
- Thumbnails are a single 390-pixel size; HiDPI tiles wider than that are upscaled.
- Temporary files left by process termination are not swept at startup. Failed best-effort deletion and rescan version changes can also leave orphan JPEGs, until Clear all thumbnails sweeps the owned directory. Ordinary scan and asset cleanup remains reference-driven.
- Filesystem publication and SQLite updates are not one atomic transaction. A crash between rename and compare-and-set leaves a valid unreferenced target; a cleanup deletion failure can leave an unreferenced file; a `thumb://` `200` is sent only after its database update was accepted.
- Failure rows use `source_record_version`; migration discards old markers whose source version is unknown.

## Safe change checklist

1. Preserve one target identity across every entry point. The key already carries a cache version (`THUMB_CACHE_VERSION`); if identity inputs or rendering rules change, bump it and plan regeneration/cleanup of orphaned targets; test same-path versions, same-second modifications, and old database references.
2. Keep temporary writes and final publication in the same directory. Test decode/render failure, stale temporary files, an already-present final target, and concurrent waiters without exposing a partial JPEG.
3. For image changes, test the 390-pixel bound, aspect preservation, exact `1.6` crop threshold, 96-pixel top bias and clamp, EXIF orientation on both decode paths (quarter turns, mirrors, missing and invalid values), GIF decoding, RGB/JPEG conversion, and small/zero-dimension edge behavior.
4. For video changes, test every seek boundary, unknown duration, zero-second fallback, scale/output arguments, nonzero exit, missing executables, probe parsing, 12/45-second timeouts, and child termination.
5. Keep ffmpeg and ffprobe discovery aligned. Exercise resource, executable-adjacent, `/usr/bin`, and system `PATH` layouts.
6. Preserve scheduler target de-duplication, waiter fan-out (channel and callback), priority promotion, LIFO Interactive and FIFO High/Low order, image progress around blocked videos, mode-specific worker bounds, the browsing two-video cap, scoped bulk restoration, panic-safe terminal results, and the `MAX_PENDING_JOBS` queue bound. Startup must keep refusing to run when worker threads fail to spawn.
7. Keep the `thumb://` parser strict (numeric ID, hex version, known flags only, no paths), `thumbnailUrl` the only URL builder, `thumb_version` a prefix of the target stem, and the cache headers tied to the version match. Follow the [IPC contract](../architecture/ipc-contract.md) for any transport change.
8. Preserve the one-`<img>` tile, per-source load/retry/failure state keyed by each `src` change, the quick retry budget before the placeholder and the capped (30 s) backoff with one timer per mounted component, the cached-only pause rule, the one-way `p=1` drop for a visible tile whose picture has not arrived (never for a loaded picture or during a pause) and the CSS-only spinner. Test source changes during a pending retry, a returning source after a failure, unmount during a pending retry, and a cached-only miss after the pause.
9. Treat cancellation as a partial commit. Test cancellation before enqueue, while below and at the CPU-based submission window, during final drain, with image/video jobs still running, and verify summary counts, failure rows, published files, and subsequent reconciliation.
10. Keep lock order consistent for generation, clear, rename/delete, scan-root removal, library clear, and bundle replacement. Test that exclusive cleanup cannot race a demand reader and that best-effort filesystem failure leaves truthful counts and recoverable database state.
11. When changing failure policy, test count reset on asset-version change, stale-row cleanup, render-all skip, retry-failed ordering, success clearing, missing sources (with and without a cached thumbnail), and repeated failures. Use the source record version for failure writes and the precise fingerprint for target identity.
12. Run Rust formatting and focused `thumbs`, scheduler, service, database, and command tests; run the `ThumbnailImage` and gallery tests; then exercise a packaged desktop build with real image, GIF, short/long video, system tool discovery, cancellation, and cleanup.
