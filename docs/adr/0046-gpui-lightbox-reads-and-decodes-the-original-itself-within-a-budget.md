# 0046: The GPUI lightbox reads and decodes the original itself, within a budget, and one session of the client crate decides what its view does

- Status: Accepted
- Date: 2026-11-22
- Areas: GPUI port, lightbox, memory, security surface
- Related: [lightbox](../subsystems/lightbox.md#gpui-port-the-lightbox-view), [GPUI port plan](../plans/gpui-port/README.md) (epic E16, decisions D4 and D8), [ADR 0036](0036-gpui-second-adapter-in-its-own-workspace.md), [ADR 0037](0037-gpui-client-backend-port-and-model-convention.md), [ADR 0039](0039-gpui-overlay-layers-and-controls.md), [ADR 0042](0042-gpui-gallery-grid-logical-offset-and-bounded-pictures.md), [ADR 0045](0045-gpui-lightbox-model-embedded-with-a-ticket-range-and-tag-saves-as-changes.md)

## Context

The Solid lightbox gives the path of the selected asset to the webview (`toMediaSrc`, the asset protocol with scope `**`). WebKit reads the file, decodes it, scales it, animates a GIF and keeps its own limits. GPUI has none of that: an image element decodes a whole file into BGRA pixels, keeps every frame of an animation and uploads the frame it draws as one texture. A texture larger than the GPU's limit is refused, a decoded picture of 200 megapixels is 800 MB in memory and as much again on the GPU, and the epic names the decode memory limit as its one risk. The epic allows no new dependency, so the adapter cannot name the `image` crate to scale a decoded picture or to decode a single frame; it has `gpui::Image::to_image_data` only.

The plan shows a GIF as its first frame and a video as a placeholder (decision D8). GPUI's decoder decodes every frame of a GIF.

`LightboxModal.tsx` also holds a dozen signals and effects that belong to one opening of the lightbox: the side panel, the fading controls, the confirmation, the Information panel, the tag draft, the viewer's zoom and pan, and the rules that need several of them at once (what Escape closes, when the viewer's keys are on, where the focus goes). [ADR 0045](0045-gpui-lightbox-model-embedded-with-a-ticket-range-and-tag-saves-as-changes.md) left the four machines to the view.

## Options considered

1. **GPUI's `img` element with the path.** No code, but it decodes on GPUI's asset loader without a budget, animates the GIF (which the plan defers), caches the decoded picture in the application's asset cache without a bound, and gives the view no moment at which the picture's own size is known.
2. **A `Backend` port method that returns the original's bytes.** It keeps every file access behind the port, but the core has no such use case (the Tauri adapter does not read originals either), the bytes would cross the port as one `Vec`, and the decode would still be the adapter's.
3. **The adapter reads the file and decodes on GPUI's background executor, with the policy in the client crate (chosen).**
4. **Scaling an oversized picture down.** It needs the `image` crate in the adapter's manifest, which the epic does not allow.

For the view state: keep the machines as separate fields of the view and write the cross-rules in the view (as the Solid component does), or put one `Session` into the client crate that owns them (chosen), so that the rules are tested without a window.

## Decision

- **Who reads.** `media_tagger_gpui::media::Originals` reads the file named by `SelectedAsset::path` (the path of the backend's details, or the preview path of a GIF row) with `std::fs` on GPUI's background executor and decodes it there with `gpui::Image::to_image_data`. It never runs on the UI thread and is no backend call. It holds the picture of one source; another source drops it, and an answer for a source that is no longer shown is dropped by a generation. One load runs at a time: a decode that a background thread has begun cannot be stopped, so a source that is shown meanwhile waits for it to end, the running load gives up before it reads and again before it decodes once its source is no longer shown, and the sources passed in between are never read. The budget below is therefore the budget of the lightbox, not of each background thread. The texture of a dropped picture is taken out of the window's atlas with the next frame.
- **A read that does not return.** A decode always ends; a read may not (a file on a network or FUSE mount that stopped answering blocks its thread without a limit), and it cannot be stopped either. The read of the shown source is waited for as long as it is shown, as a webview waits for its image, and the stage shows a spinner once that has taken a moment (the tile loader's delay). The read of a source that is no longer shown keeps the next one waiting for at most `READ_DEADLINE` (10 s): then it is given up, which means it is left to return on its thread, where its bytes are dropped, and the shown source is loaded. A read that was given up still holds a background thread and at most the bytes of its file, so at most `reads_allowed` reads run at once, the running one included: one background thread stays free and the number never exceeds three (`MAX_READS`). When that many have been given up, the shown source waits until one of them returns and is loaded then.
- **What may be decoded** is decided in `media_tagger_client::lightbox::media`, without a GUI: the format comes from the file's first bytes, never from its name (PNG, JPEG, WebP, BMP, GIF, which is what the indexer lists); a file over 512 MiB is not read, and the adapter holds that against what it reads as well as against the length the file reports: it reads a regular file only (a link is followed, as the asset protocol follows it; a device, a pipe or a directory that an indexed path names by now is refused) and stops one byte past the budget; the size comes from the header (`probe_dimensions`), else from the library's stored dimensions; a picture with a side over 16 384 pixels or with more than 192 megapixels over all the frames the decoder keeps is not decoded. A refusal, an unreadable file, an unknown format and a failed decode all show `lightbox.mediaError.image`. A texture the GPU refuses at draw time counts as a failure too. No limit of GPUI's decoders lies below this budget: GPUI builds its decoder with `image::ImageReader::into_decoder` (image 0.25.10), which holds the reader's default limits against the picture's dimensions only, and those have no default; the default allocation limit of 512 MiB reaches the PNG decoder's own buffers (one line, the ancillary chunks), not the decoded picture, and `ImageReader::decode`, which would reserve the picture against it, is not what GPUI calls. A PNG of 134 megapixels with alpha (538 MB decoded) and a JPEG of 185 megapixels were decoded through the adapter's decode function to check this. The budget counts the pixels that are kept; while a picture is decoded it takes more for a moment (an RGB picture is decoded to three bytes a pixel and then converted to four, and a decoder has working buffers of its own).
- **GIF.** `gif_first_frame` cuts the file down to its header, global colour table, first picture with its graphic control, and trailer, so the decoder holds one frame whatever the length of the animation. The stage shows it with a GIF chip. An animated WebP is decoded with every frame, within the same pixel budget, and its first frame is drawn.
- **Video.** Nothing is read. The stage shows the asset's thumbnail as a poster (one extra demand of `Thumbnails`, `sync_poster`), the Video label, its metadata and `lightbox.placeholder.videoUnavailable`. `f` and the fullscreen button are taken and do nothing for a video.
- **Session.** `media_tagger_client::lightbox::Session` is one opening of the lightbox. It owns `Sidebar`, `Activity`, `GroupClipboard`, `DeleteConfirm`, the viewer (`ImageControls`, a port of `createImageControls.ts` over `pan_zoom.rs`) and `Fullscreen`, plus the Information flag and the tag draft. It answers Escape, a press on the backdrop, the viewer's keys and the focus after the panel or the confirmation changed, and it computes the fades and the slide from the time it is given. The view makes it when an asset is selected and drops it when the fade-out has ended; it draws a `Shown` copy of the model's values, which it keeps while the closed lightbox fades.
- **Fullscreen through the window.** The viewer's fullscreen asks the window manager for a fullscreen window and lays the dialog out over all of it. `Fullscreen` remembers whether it made the window fullscreen and takes back only that; a window the user took out of fullscreen takes the lightbox with it. GPUI can only toggle a window and the window answers later; a second toggle before the answer takes the first back on X11 and repeats it on Wayland, so `WindowFullscreen` (kept by the view for the window's lifetime) never toggles a window whose answer is due and toggles it once more when it has answered and the other state is wanted. A request the window has not answered within three seconds (`WINDOW_ANSWER_TIMEOUT`) is forgotten: a window manager that never grants it would otherwise leave it in flight for the window's lifetime, and a window the user made fullscreen later would be taken for its answer and toggled straight back out. Within those seconds the two cannot be told apart and the window is toggled back; a grant that comes later than that, after the lightbox left fullscreen, leaves the window fullscreen. Escape leaves fullscreen before it closes anything, as a browser's Escape leaves the fullscreen of an element.
- **Double click.** `double_click_zoom_factor` is ported and stays unbound, as in the Solid modal: a click zooms one step in, and a double click is two clicks.

## Consequences

- The adapter opens media files by path. Its scope is what the Tauri asset protocol's is (every path the library's details name); narrowing either is the open topic recorded in the [system overview](../architecture/system-overview.md).
- A picture over the budget is not shown in the GPUI lightbox, where the Tauri lightbox leaves the limit to WebKit. Showing it scaled down needs a decoder dependency and its own decision.
- Reads that were given up add to the budget: up to two files' bytes (each at most 512 MiB) beside the load that runs, until those reads return. After three reads on a mount that stays silent, or on a machine whose background executor has two threads, where no read is given up, the lightbox shows the spinner for every picture until a read returns or the application is restarted; the webview loads each image on its own and has no such limit.
- A strongly reduced picture is sampled without mipmaps, so it can alias where the webview's is smooth; the picture is exact at and above its own size.
- AVIF, HEIC and other formats the indexer does not list show the media error, also when a file with a listed extension holds one.
- Animation of GIFs (epic E20) replaces `gif_first_frame` with a bounded frame cache; native video (epic E21) replaces the placeholder and gives `Session::toggle_fullscreen` its video branch.
- The rules of one opening are tested in `lightbox/session.rs`, `image_controls.rs`, `pan_zoom.rs` and `media.rs` without a window; the view's tests need a window only for what is drawn and focused.
